2. Fundamentos del Desarrollo Web

Diapositivas 6–11

Antes de escribir código: quién pide qué, a quién, y cómo viaja la información.

Diap. 6Separador: Fundamentos del Desarrollo Web

Diapositiva de portada de sección. A partir de acá se explica el "panorama completo" del desarrollo web: las dos grandes partes (frontend y backend), los conocimientos transversales y las herramientas.

Diap. 7Las 4 áreas del desarrollo web

Una aplicación web tiene un lado cliente (frontend), un lado servidor (backend), conocimientos que atraviesan a ambos y herramientas para trabajar.

1) Frontend (cliente)

  • Lenguajes esenciales: HTML, CSS y JavaScript. Son los únicos que el navegador entiende de forma nativa.
  • Frameworks y bibliotecas: React, Vue.js, Angular → ayudan a construir interfaces grandes organizadas en componentes.
  • Preprocesadores CSS: SASS, LESS → CSS con variables, anidamiento y funciones, que luego se "compila" a CSS normal.
  • Gestores de paquetes: npm, yarn → instalan librerías de terceros (npm install react).
  • Bundlers y transpiladores: Webpack, Babel, Vite → juntan muchos archivos en pocos y convierten JS moderno a uno compatible.

2) Backend (servidor)

  • Lenguajes/entornos: JavaScript (Node.js), Python (Django/Flask), PHP, Java (Spring), C# (.NET), Ruby (Rails).
  • Componentes clave: servidor web (Nginx, Apache), framework de backend y base de datos.
  • Conceptos: Routing (qué hacer según la URL y el método HTTP), APIs REST/GraphQL (el "idioma" con el que frontend y backend se hablan), autenticación/autorización (quién sos y qué podés hacer; con JWT, OAuth, etc.).

3) Conocimientos generales

  • Protocolos y arquitectura: HTTP/HTTPS, DNS, IP, URL, dominios, modelo cliente-servidor y ciclo de vida de una petición.
  • Buenas prácticas: seguridad, performance, accesibilidad (a11y: "a" + 11 letras + "y"), responsive y control de versiones (Git).
  • Testing y mantenimiento: tests unitarios, de integración y end-to-end (e2e); CI/CD (GitHub Actions, Jenkins); documentación.

4) Herramientas y flujos modernos

  • Editores: VS Code, WebStorm, Visual Studio · DevTools del navegador.
  • Contenedores/entornos: Docker, Vagrant · Despliegue en la nube: Vercel, Netlify, Heroku, AWS.
💡 Para el parcial

Saber ubicar cada tecnología en su columna: ¿React es frontend o backend? (frontend) ¿Nginx? (backend: servidor web) ¿JWT? (backend: autenticación) ¿Vite? (frontend: bundler/herramienta de build).

Diap. 8IP, Dominio, DNS y URL

Escribís un nombre (dominio), el DNS lo traduce a un número (IP) y el navegador se conecta a esa IP para pedir el recurso que indica la URL.

  • IP: dirección numérica única que identifica a un dispositivo en una red (ej. 142.250.217.46). Es como el número de teléfono de una computadora.
  • Dominio: nombre fácil de recordar que apunta a una IP (ej. www.google.com). Es como el nombre del contacto en tu agenda.
  • DNS (Domain Name System): sistema que traduce un dominio a su IP. Es la "guía telefónica" de internet.
  • URL: dirección completa que escribís en el navegador; indica protocolo, servidor, recurso y parámetros.

Paso a paso: 1) escribís la URL → 2) el DNS convierte www.google.com en 142.250.217.46 → 3) tu navegador usa esa IP para conectarse al servidor de Google → 4) le pide /search?q=chatgpt por HTTPS → 5) recibe HTML y lo dibuja.

⚠️ Ojo

La IP de Google del ejemplo puede variar: los sitios grandes tienen muchas IPs y el DNS te da una cercana a vos. También faltan partes opcionales de la URL: el puerto (:443, implícito en https) y el fragmento (#seccion, que no se envía al servidor — ¡esta guía usa fragmentos como #d8!).

Diap. 9Visión simplificada: cliente → internet → servidor

El cliente envía una solicitud HTTP/S (la URL) a través de internet; el servidor responde con un documento HTML.

  • Cliente: normalmente el navegador. Pide recursos.
  • Internet: la red de redes por la que viajan los paquetes (routers, proveedores, etc.).
  • Servidor: computadora que está "escuchando" pedidos y devuelve respuestas (HTML, CSS, imágenes, JSON…).

Cada respuesta HTTP trae un código de estado: 200 OK, 404 no encontrado, 500 error del servidor, etc. Lo vas a ver en la pestaña Network de las DevTools.

Diap. 10En nuestra local: el "servidor web" por dentro

Lo que llamamos "servidor" suele ser una cadena: servidor HTTP/proxy → servidor de aplicación → base de datos.

  • Servidor HTTP/Proxy: recibe las conexiones, sirve archivos estáticos (HTML, CSS, imágenes) y reenvía lo dinámico a la aplicación. Puede manejar HTTPS y balanceo.
  • Servidor de aplicación: ejecuta tu lógica de negocio (validar, calcular, consultar datos).
  • Base de datos: guarda la información de forma persistente.

"En nuestra local" significa que en tu computadora podés tener todo esto corriendo a la vez (por ej. el backend en localhost:5000 y el frontend en localhost:5173). localhost = tu propia máquina (IP 127.0.0.1).

Diap. 11Caso de uso real (CaminsDrive, UPC)

En producción las capas se multiplican: balanceador de carga, varios servidores frontend y un backend con servicios especializados.

  • Balancer (balanceador): reparte las peticiones entre varias copias del servidor frontend para soportar más usuarios y tolerar fallos. Entra por https y adentro de la red habla http.
  • Frontend: varias instancias idénticas (nginx + ownCloud). Los "⋮" indican que puede haber tantas como se necesite (escalado horizontal).
  • Backend: OpenLDAP (usuarios y autenticación), NFS (sistema de archivos en red con los archivos de usuarios y de la aplicación) y MySQL (base de datos).
  • Los íconos de fuego son firewalls: filtran el tráfico entre zonas.
⚠️ Ojo con la palabra "frontend"

Acá "Frontend" significa la capa de servidores que da la cara a los usuarios (un término de infraestructura), no el código HTML/CSS/JS. Es el mismo concepto ("lo de adelante") aplicado a servidores.

3. Frontend y tipos de renderizado

Diapositivas 12–19

Qué es el frontend, qué contiene y las distintas formas de generar el HTML que ve el usuario.

Diap. 12Frontend

Es todo lo que el usuario ve y con lo que interactúa en el navegador.

Se construye con tres capas que trabajan juntas:

  • HTML → estructura (qué hay: un título, un botón, una tabla).
  • CSS → estilos visuales (cómo se ve: colores, tamaños, posiciones).
  • JavaScript → lógica (qué hace: validar, pedir datos, mostrar/ocultar).

Separar las tres capas en archivos distintos (index.html, styles.css, app.js) es una buena práctica: cada cosa en su lugar.

Diap. 13Frontend — ¿Qué contiene?

Todos los componentes visuales e interactivos de la aplicación, más las cualidades de usabilidad.

  • Componentes: menús, formularios, botones, imágenes, gráficas, planillas (tablas).
  • Interacción: animaciones, validaciones (avisar que falta un campo antes de enviar), navegación entre páginas.
  • Responsive: que se adapte a celular, tablet y escritorio.
  • Accesibilidad: que la usen personas con discapacidad (lectores de pantalla, navegación con teclado, buen contraste, textos alternativos en imágenes).
💡 Dato

La validación del frontend es por comodidad del usuario; el backend siempre debe volver a validar, porque cualquiera puede saltearse el JS del navegador.

Diap. 14Frontend — Renderizar

Renderizar = transformar código (HTML, CSS, JS) en una interfaz visual e interactiva en la pantalla.

Dentro del navegador, "procesar el código" implica: leer el HTML y armar el DOM (árbol de elementos), leer el CSS y armar el CSSOM, combinarlos, calcular posiciones (layout) y pintar los píxeles (paint). Lo hace el motor de renderizado.

Diap. 15Tipo 1: Server-Side Rendering (SSR)

El servidor arma el HTML completo en cada solicitud y lo manda listo al navegador.

Cuándo conviene: cuando el contenido cambia seguido y necesitás buen SEO (que Google indexe bien la página). Ejemplos: blogs, e-commerce, portales de noticias.

✅ Pros❌ Contras
Buena performance inicial (el usuario ve contenido enseguida).
SEO optimizado: el HTML ya trae el texto.		Carga más lenta al pasar de una página a otra (se recarga todo).
Requiere más recursos del servidor (trabaja en cada visita).

Frameworks: Next.js (modo SSR), Laravel (PHP), Ruby on Rails, ASP.NET MVC.

⚠️ Errata

En la diapositiva dice "Buena performance ideal"; se refiere a buena performance inicial (primer pintado rápido).

Diap. 16Tipo 2: Client-Side Rendering (CSR)

El navegador recibe un HTML casi vacío y JavaScript construye la interfaz.

Ejemplos: dashboards, paneles de usuario, SPAs.

✅ Pros❌ Contras
Navegación fluida (no recarga la página).
Separación clara frontend/backend (el backend solo da JSON).		Peor SEO: al principio el HTML no trae contenido.
Primera carga más lenta (hay que bajar y ejecutar el JS).

Frameworks: React (con Vite o CRA), Vue, Angular.

⚠️ Dato actualizado

CRA (Create React App) fue deprecado oficialmente en 2025; hoy se recomienda Vite (o un framework como Next.js).

Diap. 17Tipo 3: Single Page Application (SPA)

Un caso particular de CSR: toda la app vive en un único index.html y la navegación no recarga la página.

Cuando hacés clic en "Bandeja de entrada" o "Enviados" en Gmail, la URL cambia pero la página no se recarga: JavaScript reemplaza solo la parte que cambia. Ejemplos: Gmail, Trello, Google Drive.

✅ Pros❌ Contras
UX fluida, parecida a una app de escritorio.
Ideal para apps con muchas interacciones.		Manejo más complejo del estado y las rutas.
SEO limitado (se usan técnicas de prerendering).

Relación: toda SPA es CSR, pero no todo CSR es una SPA (podrías tener varias páginas, cada una renderizada en el cliente).

Diap. 18Tipo 4: Progressive Web App (PWA)

No es un método de renderizado: es un enfoque para que una web se comporte como app instalable y funcione offline.

  • Funciona offline (o con mala conexión).
  • Se ve como app móvil (pantalla completa, ícono propio).
  • Se instala en el dispositivo desde el navegador.

Ejemplo: Spotify web app. Pros: carga rápida, experiencia tipo app, funciona offline. Contra: compleja de configurar.

Requiere: Service Workers — scripts que el navegador ejecuta en segundo plano, interceptan las peticiones de red y pueden responder desde una caché (por eso funciona sin internet). También necesita un archivo manifest.json (nombre, íconos, colores) y servirse por HTTPS.

Diap. 19Tipos 5 y 6: MPA y SSG

MPA = cada página es un HTML distinto que se recarga; SSG = los HTML se generan una sola vez al compilar.

5 · MPA (Multi-Page Application)

El modelo "clásico": cada clic en un enlace pide un HTML nuevo al servidor y se recarga la página completa. Ejemplos: sitios tradicionales en PHP, WordPress, ASP. Los ejercicios #17 a #20 de esta unidad son MPA (index.html ↔ doctors.html).

6 · SSG (Static Site Generation)

Las páginas se generan en el momento del build (antes de publicar) y quedan como archivos estáticos. Súper rápidas y baratas de hospedar (¡como GitHub Pages!). Ideal cuando el contenido cambia poco: blogs, landing pages, portfolios. Herramientas: Astro, entre otras (Hugo, Jekyll, Next.js en modo export).

❓ ¿Lo entendiste?

Un portal de noticias que necesita aparecer bien en Google, ¿SSR o CSR?
SSR: el HTML llega completo y los buscadores lo indexan mejor.
¿Por qué una app CSR tiene peor SEO?
Porque el HTML inicial está vacío (<div id="root">); el contenido aparece recién cuando se ejecuta el JS.
¿Qué tecnología hace que una PWA funcione offline?
Los Service Workers (con caché).
¿Toda SPA es CSR?
Sí. La SPA es un tipo particular de CSR.

5. HTML (HyperText Markup Language)

Diapositivas 25–34

El esqueleto de toda página: elementos, atributos, estructura del documento y etiquetas semánticas.

Diap. 25¿Qué es HTML?

Lenguaje de marcado (no de programación) que define la estructura del documento con etiquetas.

  • Define la estructura usando etiquetas como <h1>, <p>, <img>.
  • El navegador lo interpreta y lo muestra visualmente.
  • Es el esqueleto de la página: HTML + CSS (estilos) + JS (comportamiento) forman la base del desarrollo web.
⚠️ Pregunta clásica

¿HTML es un lenguaje de programación? No: es de marcado. No tiene variables, condicionales ni bucles; solo describe qué es cada parte del contenido. "HyperText" = texto con enlaces a otros textos.

Diap. 26Anatomía de un elemento

Elemento = etiqueta de apertura + contenido + etiqueta de cierre.

  • Etiqueta de apertura: nombre del elemento (ej. p de párrafo) entre < >. Indica dónde empieza.
  • Contenido: lo que va adentro (texto u otros elementos).
  • Etiqueta de cierre: igual a la de apertura pero con / antes del nombre. Indica dónde termina.
⚠️ Importante (lo remarca la diapositiva)

Si no cerrás un elemento, algunos navegadores "adivinan" dónde termina y completan la estructura solos. NUNCA hay que confiar en eso: siempre cerrá tus elementos, porque cada navegador puede adivinar distinto y romper el diseño.

Diap. 27Anidamiento y casos especiales

Se pueden poner elementos dentro de otros, pero se cierran en orden inverso al que se abrieron.

En el ejemplo incorrecto el navegador intenta corregirlo y termina poniendo en negrita "muy gruñón." — el resultado no es el que querías. Pensalo como cajas: la caja de adentro se cierra antes que la de afuera (última en abrir, primera en cerrar).

Diap. 28Atributos

Información extra del elemento que va en la etiqueta de apertura: nombre="valor".

Un atributo debe tener:

  1. Un espacio entre el nombre del elemento (o el atributo anterior) y el atributo.
  2. El nombre del atributo seguido de =.
  3. El valor entre comillas de apertura y cierre.

Casos particulares: los atributos booleanos no necesitan valor; con solo estar presentes ya están activos: <input required>, <input disabled>, <input type="checkbox" checked>.

Diap. 29Anatomía de un documento HTML

Todo documento tiene: <!DOCTYPE html>, y dentro de <html> un <head> (info) y un <body> (lo visible).

  • <!DOCTYPE html>: indica que es HTML5. No es una etiqueta, es una declaración.
  • <html>: elemento raíz. lang="es" le dice al navegador y a los lectores de pantalla el idioma.
  • <head>: metadatos (no se ven): codificación, título de la pestaña, enlaces a CSS y scripts, viewport.
  • <body>: el contenido visible: textos, imágenes, enlaces, etc.

6. Formularios HTML

Diapositivas 35–39

Diap. 35Forms

Un formulario permite al usuario ingresar datos y enviarlos a un servidor o procesarlos en el cliente con JS.

  • action: URL a la que se envían los datos (si no se pone, se envía a la misma página).
  • method: GET (los datos van en la URL: ?nombre=Ana; para búsquedas) o POST (van en el cuerpo de la petición; para crear/guardar datos o enviar contraseñas).
  • Cada campo debe tener un atributo name: es la "clave" con la que llega el dato al servidor.

Más adelante (tema 19) el formulario se procesa en el cliente con JavaScript, usando e.preventDefault() para evitar que la página se recargue.

Diap. 48Cascada, especificidad y herencia

Tres mecanismos que deciden qué estilo termina aplicándose a cada elemento.

  • Cascada: el orden de las reglas SÍ importa. Si dos reglas tienen la misma especificidad, gana la que está más abajo.
  • Especificidad: cuando reglas con selectores distintos chocan en un mismo elemento, gana el selector más específico (aunque esté antes).
  • Herencia: algunas propiedades que le ponés a un padre las heredan sus hijos (ej. color, font-family, font-size) y otras no (ej. border, margin, padding, width, background).

Podés forzar herencia con inherit: button { font: inherit; }.

Diap. 57Flexbox — ¿Qué es?

Sistema de diseño unidimensional: acomoda elementos en una fila (row) o en una columna (column).

Fue creado para alinear y distribuir espacio entre los elementos de un contenedor. Se activa en el padre y afecta a sus hijos directos:

Diap. 58Flexbox — Características

  • Flexibilidad: flex-grow (cuánto crece), flex-shrink (cuánto se encoge), flex-basis (tamaño inicial). Atajo: flex: 1 = "ocupá el espacio que sobra".

Sistema de diseño bidimensional: organiza en filas y columnas al mismo tiempo.

  • Soporta alineación avanzada y áreas con nombre (grid-template-areas): dibujás el layout con palabras.
  • Se adapta muy bien a diseños responsivos: con una media query redibujás las áreas.

11. Diseño responsive, media queries y position

Diapositivas 65–73

Diap. 65Diseño responsive — Fundamentos

Que el sitio se adapte a cualquier pantalla usando tres herramientas: layouts fluidos, medios flexibles y media queries.

  1. Diseño fluido: usar unidades relativas (%, em, rem, vh, vw) en vez de px fijos. Ej.: en lugar de width: 600px, usar width: 80% (o max-width: 600px; width: 100%).
  2. Imágenes y contenido flexibles: img { max-width: 100%; height: auto; } → la imagen nunca es más ancha que su contenedor. Videos e iframes también deben adaptarse.
  3. Media queries: aplicar estilos distintos según el tamaño de la pantalla. Ej.: un menú horizontal en escritorio que en móvil se vuelve desplegable (ejercicio #22).

Diap. 66Metaetiqueta viewport

Diap. 67Media queries

Bloques de CSS que solo se aplican si se cumplen ciertas condiciones (tamaño de pantalla, tipo de medio, orientación…).

Consta de tres partes:

  1. Un tipo de medio: para qué medio es el código (screen, print, all).
  2. Una expresión de medio: la condición que debe cumplirse ((min-width: 768px), (orientation: landscape)).
  3. Un conjunto de reglas CSS que se aplican si la prueba pasa y el tipo de medio es correcto.

min-width: 768px = "desde 768px en adelante"; max-width: 768px = "hasta 768px". Lectura: MDN — Media queries.

12. JavaScript: fundamentos

Diapositivas 74–80

Diap. 74JavaScript

Lenguaje de programación interpretado, multiparadigma y dinámico, que corre en el navegador y también en el servidor.

  • Interpretado: no se compila de antemano a un ejecutable; el motor lo lee y ejecuta (hoy con compilación JIT, ver diap. 75).
  • Multiparadigma: permite programar orientado a objetos (clases), funcional (funciones como valores, map/filter) y procedural/imperativo (paso a paso con for, if).
  • Dinámico: el tipo de una variable se decide en tiempo de ejecución y puede cambiar (let x = 5; x = "hola";).
  • Permite implementar funciones complejas en páginas web (del lado cliente) o en el servidor (Node.js).

Diap. 92Objetos

Un objeto es una colección de propiedades, cada una formada por una clave (nombre) y un valor.

Es fundamental saber trabajar con objetos porque se usan para modelar cosas del mundo real (un paciente, un doctor, una especialidad) y para manipular datos: los JSON que vienen de una API son objetos y arrays de objetos.

17. Event Loop

Diapositivas 108–113

Cómo un lenguaje de un solo hilo puede esperar un fetch sin congelar la página.

Diap. 108Event Loop — Los 4 pilares

Mecanismo que permite a JS ejecutar operaciones asincrónicas y no bloqueantes usando un solo hilo. JS no es multihilo.

"Un solo hilo" = JS hace una cosa a la vez. Si esperara 2 segundos a que llegue un fetch, la página se congelaría. La solución: delegar la espera al navegador y seguir; cuando la tarea termina, su callback se pone en una cola, y el Event Loop lo ejecuta cuando JS está libre.

Diap. 109Event Loop — Call Stack

  • Acá se ejecuta el código sincrónico.
  • Funciona como una pila LIFO (Last In, First Out): la última función que entra es la primera que sale.

Si una función se llama a sí misma sin fin, el stack se llena: error Maximum call stack size exceeded (el famoso "stack overflow").

Diap. 110Event Loop — Web APIs

Operaciones que provee el navegador (no el motor de JS) y que trabajan "en segundo plano":

  • setTimeout / setInterval (temporizadores)
  • fetch (peticiones HTTP)
  • Eventos del DOM / addEventListener

JS le dice al navegador "avisame cuando pase X" y sigue ejecutando lo que sigue. Cuando X ocurre, el navegador pone el callback en la cola correspondiente.

⚠️ Errata

"Aquí entras las operaciones" → "aquí entran".

Diap. 111Event Loop — Callback Queue

  • También llamada Task Queue o Macrotask Queue.
  • Una task es una unidad de trabajo que será ejecutada.
  • Acá esperan los callbacks de operaciones asincrónicas como setTimeout, setInterval y los eventos (click…).

Es una cola FIFO (el primero que llega es el primero en salir).

Diap. 112Event Loop — Microtask Queue

  • Es una cola de mayor prioridad que la de tareas.
  • Contiene: Promise.then, .catch, .finally, lo que sigue a un await, y queueMicrotask.
⚠️ Errata

"encotnramos" → "encontramos".

Diap. 113Event Loop — Resumen

El Event Loop siempre:

  1. Ejecuta todo lo del Call Stack.
  2. Cuando el stack está vacío: ejecuta todas las microtareas.
  3. Luego ejecuta una tarea (macrotask).
  4. Repite.

Diap. 126IndexedDB en código

Conceptos: base de datos (con versión) → object store (como una tabla) → keyPath (la clave primaria, acá id) → índices (para buscar por otro campo) → transacciones (readonly o readwrite). Todo es asíncrono con eventos (onsuccess, onerror), a diferencia de localStorage.

Si llamás add con un id que ya existe da error; para "insertar o reemplazar" se usa put. Lo ves en DevTools → Application → IndexedDB.
